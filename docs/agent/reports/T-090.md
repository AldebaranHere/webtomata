### Target difference: 64-bit native vs. 32-bit `wasm32`

`usize` is 64-bit on native Linux (`usize::MAX = 18_446_744_073_709_551_615`) and 32-bit on `wasm32-unknown-unknown` (`usize::MAX = 4_294_967_295`). Consequently:

- On native 64-bit, `{ w in {a}* : |w| > 18446744073709551615 }` parses `usize::MAX` and hits `checked_add(1)` → `NumberTooLarge`; `{ w in {a}* : |w| >= 18446744073709551615 }` and `100000000000` parse and hit `start_len > ENUMERATION_MAX_LENGTH` → `LengthTooLarge`.
- On `wasm32`, `18446744073709551615` and `100000000000` exceed `u32::MAX`, so they overflow `parse_number()` with `NumberTooLarge`. In `language-errors.wasm.test.ts`, `{ w in {a}* : |w| > 4294967295 }` exercises `checked_add(1)` on `wasm32`, `{ w in {a}* : |w| > 18446744073709551615 }` exercises `parse_number()` overflow on `wasm32`, and `{ w in {a}* : |w| >= 1000000000 }` / `4294967295` exercise `LengthTooLarge` on `wasm32`.

## Enumeration limit and WASM stack measurement (Decision 4)

Chosen limit: **`ENUMERATION_MAX_LENGTH = 200`** (twice the web UI's `min_length` clamp of `100`).

Measured against the compiled release `wasm32` binary (`web/src/lib/engine/wasm/engine_wasm_bg.wasm`) in Node.js v24.21.0, testing the deepest recursive and constructive paths at `L = 200` and refusal at `L = 201`:

```text
predicate |w| >= 200 on {é}* -> ok: true count=1 len=200 (2.70 ms)
predicate forall prefix + |w| >= 200 on {a, b}* -> ok: true count=1 len=200 (0.66 ms)
constructive {é}^200 -> ok: true count=1 len=200 (1.91 ms)
constructive {é}* min_length=100 -> ok: true count=1 len=100 (0.55 ms)
predicate |w| >= 201 (refused) -> ok: false language.error.length_too_large (0.43 ms)
```

All 200-character paths finish in under 3 ms with no stack trap, and `wasm-pack test --node crates/engine-wasm` (debug `wasm32`) also passes cleanly.
