# 0027. Time limits on every CI job, and a faster CI in three steps

Status: accepted (the owner approved the plan on 2026-10-27). Steps A and B are described here; step C adds its part when it lands.

## Context
We measured the last 14 CI runs (2026-10-27). A pull request waited about 8 to 10 minutes for `web`, of which the browser tests were about 70%. Three runs of 14 were much slower: the step `playwright install-deps` of the job `cross-browser` spent 8 to 36 minutes in `apt-get`, because the package mirror of the runner hung until apt gave up on it. The same step takes about 30 seconds in a normal run. A job has no time limit by default except GitHub's 6 hours, so a stalled step can hold a job for that long. The cache of the repository was also over GitHub's limit of 10 GB (74 caches, 10.8 GB), mostly caches of pull requests that were already merged.

## Decision
The plan has three steps, each one pull request, and quality does not change: every check that runs today still runs on every pull request.
- **A. Stop the stalls.** Every job in every workflow has `timeout-minutes` (at most 30; `tools/check-workflows.mjs` fails the build without it). The `cross-browser` job first told apt to give up on a mirror after 15 seconds, with 3 retries, and its install steps got a limit of 6 minutes. **That did not fix the cause:** two runs on 2026-10-27 hit the limit of 6 minutes, and their logs show that the mirror of the runner (`azure.archive.ubuntu.com`) was slow, not hung: packages arrived at a few hundred kilobytes a second, so the inactivity timeout of apt never fired. Step B replaced it with the retry described there.
- **B. Split and gate.** `ci.yml` has these jobs: `rust` (unchanged), `checks` (everything that needs no browser), `e2e` (the Chrome tests in 3 shards, each test in exactly one), `lighthouse`, `cross-browser` (Firefox and WebKit as two jobs, each with only its own system libraries), and `web`, a gate. The gate waits for all of them, runs also when one failed (`if: always()`, because a skipped required check counts as passed) and is green only if every result is `success`. It keeps the name `web`, so the ruleset (required checks `rust` and `web`) is not edited, and the Firefox and WebKit tests are part of the merge gate from now on. `tools/check-workflows.mjs` fails the build if `web` does not wait for a job of the file or lacks `if: always()`. The system libraries of a browser are installed by `tools/install-browser-deps.sh`, in up to three tries of 150 seconds each: apt keeps the packages that it has downloaded, so each try goes on where the one before stopped, and from the second try on the main archive (`archive.ubuntu.com`) is used in place of the slow mirror of the runner. The first version of this retry wrapped `playwright install-deps` in `timeout`, and it did not work either (PR 67, first run): `timeout` stopped only the `pnpm` process, the `apt-get` that Playwright had started as root went on, and the step ran until its own limit. The script asks Playwright what is missing (`install-deps --dry-run`) and runs `sudo timeout -k ... apt-get` itself, so the limit applies to apt. It has tests with fake `apt-get`, `sudo` and `pnpm`, including an apt that ignores the polite stop. The Firefox and WebKit jobs are part of the gate, so a stalled install must not fail the merge for a reason that has nothing to do with our code. A push to `dev-initial` no longer starts a second run: the run of its pull request covers it. This matters now that a run has nine jobs, because a free repository runs at most 20 jobs at once.
- **C. Caches.** Only runs on `staging` and `main` save caches (`save-if` of the Rust cache, and `actions/cache/restore` plus a `save` step that has the same condition for the Playwright browsers); pull requests restore the caches of `staging` and `main` and save nothing, because a cache that a pull request saves can only be used by that pull request. A new workflow, `cleanup-caches.yml`, deletes the caches of a pull request when it closes (`gh cache delete`, for the caches of `refs/pull/N/merge`). It is the only workflow with `actions: write`; `tools/check-workflows.mjs` fails the build if another one has it, or if any workflow has `contents: write`. The pnpm cache of `actions/setup-node` cannot be limited this way, so it is still saved by each branch (about 150 MB), and the cleanup workflow removes the ones of pull requests.

## Consequences
- A real slow step (a first run with cold caches) must stay under the limits: 15 minutes for `rust` and `lighthouse`, 20 for `checks`, `e2e` and `cross-browser`, 5 for the gate. The normal times before step B were 1 minute for `rust`, 10 for the old `web` and 6 for `cross-browser`; the expected times after step B are in the pull request of step B and are measured there.
- A job that hits its limit fails with a clear message. It costs a re-run, instead of a silent wait of hours.
- Deleting the 46 caches of closed pull requests (6.1 GB) was done by hand on 2026-10-27, with the owner's approval; step C keeps it from growing back.
- Each of the e2e shards, the Lighthouse job and the two browser jobs builds the WASM module and the site itself (about 20 seconds with warm caches), which is cheaper than moving a build between jobs and keeps each job independent. The cost is more runner minutes, which are free for a public repository.
- Because the tests are split by file, a shard can be a little slower than the others; the gate waits for the slowest. If one shard stays far behind, the number of shards is one number in `ci.yml`.
